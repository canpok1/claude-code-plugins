---
name: retro
description: 作業メモとこれまでの文脈をもとに作業全体の振り返りを行う時に使うスキル。振り返り結果をメモに追記し、完了後にアーカイブする。
allowed-tools: Read, Edit, Write, Glob
---

## 手順

- [ ] ステップ1: 作業メモを取得・参照する
- [ ] ステップ2: これまでの文脈を整理する
- [ ] ステップ3: 振り返り観点で整理する
- [ ] ステップ4: 振り返り結果を作業メモに追記する
- [ ] ステップ5: 作業完了状態を確認する
- [ ] ステップ6: 振り返りのTryをClaudeメモリに保存する
- [ ] ステップ7: メモをアーカイブ移動する

## 注意点

- 全体
    - 各ステップで該当する目的のスキルが利用可能であれば積極的に活用すること。
    - 振り返りは事実ベースで記述すること。責任論や個人への批判にしないこと。
    - 作業メモが存在しない場合は、会話の文脈だけから振り返りを行うこと。
- ステップ1
    - 現在のブランチに対応する作業メモを取得・参照すること。
    - メモが存在しない場合はステップ2へ進むこと（文脈のみで振り返る）。
- ステップ2
    - 作業メモと会話の文脈から、以下の観点で情報を整理すること:
        - 実装内容: 何を実装・変更したか
        - 遭遇した問題: どんな問題やエラーに遭遇したか
        - 工夫した点: どのような工夫や判断を行ったか
        - 時間をかけた点: どこに時間がかかったか
- ステップ3
    - ステップ2の整理結果をもとに、以下の振り返り観点でまとめること:
        - うまくいったこと（Keep）
        - 改善すべきこと（Problem）
        - 次回以降に活かすこと（Try）
- ステップ4
    - 作業メモファイルが存在する場合、振り返り結果をメモの末尾に追記すること。
    - 以下のフォーマットで追記すること:
      ```markdown
      ## 振り返り

      ### うまくいったこと（Keep）
      - {内容}

      ### 改善すべきこと（Problem）
      - {内容}

      ### 次回以降に活かすこと（Try）
      - {内容}
      ```
    - 作業メモが存在しない場合は、`work-memo` スキルの仕組み（`get-memo-path.sh`）を使ってメモファイルを新規作成し、振り返り結果を書き込むこと。
    - 新規作成時は、目的や作業内容を会話の文脈から簡潔にまとめた上で、振り返り結果を記載すること。
- ステップ5
    - ステップ4で追記した作業メモの内容を確認し、以下の観点で作業完了状態を判定すること:
        - **チェックボックスの消化率**: 「作業内容」セクションのチェックボックス（`- [x]` と `- [ ]`）を集計し、全体の完了率を算出する
        - **振り返りセクションの有無**: 「## 振り返り」セクションが存在し、内容が記載されているか確認する
    - 判定基準:
        - チェックボックスが全て完了（消化率100%）かつ振り返りセクションが存在する → **完了**としてステップ6へ進む
        - 上記を満たさない → **未完了**と判定し、ユーザーに以下を報告して続行するか確認する:
            - チェックボックスの消化率（例: 2/5 = 40%）
            - 振り返りセクションの有無
            - 未完了のままdone/に移動してよいか、または移動せずに終了するか
    - 作業メモにチェックボックスが存在しない場合（新規作成メモや、チェックリストを含まないメモ）は、振り返りセクションの有無のみで判定すること。
- ステップ6
    - ステップ4で追記した「次回以降に活かすこと（Try）」の各項目について、Claudeメモリ（`feedback` タイプ）への保存要否を判定し、対象なら保存すること。
    - 判定基準:
        - **保存対象**: 今後の作業全般に再利用できる汎用的な学び。例:「`gh`コマンドは最初から`--json`オプションで安定化」
        - **対象外**: 特定のIssueや作業固有の内容、今回限りで再利用価値の低いもの。例:「Issue #42のAPIレスポンスを確認する」
    - 保存手順:
        1. システムプロンプトで指定されたメモリディレクトリ配下の `MEMORY.md` を読み、既存の `feedback` タイプのメモリを確認する。関連しそうな既存メモリファイルが複数ある場合は、並行Readで一括取得すること。
        2. Tryの全項目について、保存要否と既存メモリとの重複有無を先にまとめて判定する。
            - 重複しない場合: 新規メモリファイルを作成。
            - 重複する場合: 既存メモリと統合するとより汎用的な表現になるなら更新、そうでなければスキップ。
        3. 新規作成・更新するメモリファイルには以下の frontmatter を設定すること:
            - `name`: メモリの短い名前
            - `description`: 将来の関連性判断に活用できる具体的な一行説明
            - `type: feedback`
            - ファイル名は `feedback_{トピック}.md` の形式にすること（例: `feedback_retro_done.md`）
        4. 本文は以下の構造で記述すること:
            - 冒頭: ルール・学びそのもの
            - `**Why:**`: なぜこの学びが重要か（背景・理由）
            - `**How to apply:**`: いつ・どこで適用するか
        5. `MEMORY.md` の `Feedback` セクションへの追記・更新は、全Tryの判定と個別メモリファイルの書き出し完了後に1回のEditでまとめて実施すること。フォーマット例: `- [タイトル](ファイル名.md) — 一行の説明`
    - メモリの肥大化を防ぐため、保存対象は厳選すること。迷った場合は保存しない方を選ぶ。
    - 処理結果（保存・更新・スキップ、または対象なし）をユーザーに報告すること。
- ステップ7
    - メモをアーカイブ移動すること。
    - 移動先のパスを確認し、アーカイブが完了したことを報告すること。
