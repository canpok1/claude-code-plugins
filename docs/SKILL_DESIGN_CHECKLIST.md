# スキル新規作成 設計チェックリスト

スキルを新規作成する際に、以下のチェックリストを順に確認してください。
初期設計の段階で判断を済ませることで、実装後の手戻りを防ぎます。

## 1. Workflow / Atomic の判断

スキルの種類を最初に決定します。

| 観点 | Workflow | Atomic |
|------|----------|--------|
| 役割 | 複数のステップを組み合わせて目的を達成する | 単一の責務を担う |
| ステップの記述 | 「何を達成するか」（目的）のみ | 「どうやるか」（手順）を詳細に記述 |
| スキルの呼び出し | LLM が目的に合致する Atomic スキルを自動選択 | 直接実行される |
| frontmatter | `disable-model-invocation: true` を指定 | `allowed-tools` を指定 |

**チェック項目:**

- [ ] このスキルは複数の独立したステップを組み合わせるか？ → **Yes なら Workflow**
- [ ] このスキルは単一の責務に集中しているか？ → **Yes なら Atomic**
- [ ] 既存の Workflow スキルのステップとして利用されることを想定しているか？ → **Yes なら Atomic**

## 2. allowed-tools の確認（Atomic スキルの場合）

Atomic スキルでは、必要最小限のツールだけを `allowed-tools` に指定します。

**チェック項目:**

- [ ] 既存の類似スキルの `allowed-tools` パターンを確認したか？
- [ ] 不要なツールを含めていないか？（最小権限の原則）
- [ ] Bash コマンドは具体的なコマンドに限定しているか？（`Bash` ではなく `Bash(git diff *)` のように）
- [ ] スクリプトを利用する場合、`${CLAUDE_PLUGIN_ROOT}` を使ったパス指定にしているか？

**既存パターンの参考例:**

| スキル | allowed-tools |
|--------|--------------|
| tdd | `Bash, Read, Grep, Glob, Write, Edit` |
| self-review | `Bash(git diff *), Bash(git log *), Read, Grep, Glob` |
| work-memo | `Bash(${CLAUDE_PLUGIN_ROOT}/skills/work-memo/scripts/get-memo-path.sh), Bash(${CLAUDE_PLUGIN_ROOT}/skills/work-memo/scripts/move-memo.sh *), Read, Write, Edit` |

## 3. description の目的文マッチング

`description` は Workflow スキルが Atomic スキルを自動選択する際のマッチングキーとなります。

**チェック項目:**

- [ ] `description` は「〜する時に使うスキル。」の形式で、**いつ使うか**が明確か？
- [ ] Workflow 側のステップ記述と目的ベースで一致するか？
- [ ] 類似する既存スキルの `description` と差別化できているか？

**良い例:**

```
# Workflow 側のステップ
- [ ] ステップ3: 自分が書いたコードをレビューし、指摘があれば修正する

# Atomic 側の description（目的が一致）
description: 自分が書いたコードの変更内容をレビューし、指摘点を洗い出す時に使うスキル。
```

## 4. 知識配置の確認

他スキルが持つべき情報が自スキルに漏れていないかを確認します。

**チェック項目:**

- [ ] 他スキルのディレクトリ名やパスをハードコードしていないか？
- [ ] 他スキルの内部コマンドやスクリプトを直接呼び出していないか？
- [ ] 自スキルが持つべき情報と、他スキルが持つべき情報の境界は明確か？

**原則:**

- 各スキルは自身の責務に必要な知識だけを保持する
- 他スキルの実装詳細（ディレクトリ構造、スクリプトパス等）に依存しない
- 連携が必要な場合は、目的ベースの記述で LLM に委ねる

## 5. 既存スキルとの連携方式

他スキルとの連携インターフェースが目的ベースになっているか確認します。

**チェック項目:**

- [ ] Workflow スキルのステップは「何を達成するか」だけを記述し、具体的な Atomic スキル名を指定していないか？
- [ ] Atomic スキル内で他の Atomic スキルを直接呼び出す必要がある場合、そのインターフェースは目的ベースか？
- [ ] 新しいスキルの追加によって、既存の Workflow スキルのステップと意図せず競合しないか？

**確認手順:**

1. 既存の Workflow スキル（`solve-issue` 等）のステップを読み、新しいスキルがどのステップで選択されるか確認する
2. 同じステップで選択される可能性がある既存 Atomic スキルとの `description` の差異を確認する
3. 競合する場合は `description` の表現を調整し、適切に選択されるようにする

## 6. README スキル一覧への反映

スキルの新規追加・削除、または `description` の変更を行った場合、READMEのスキル一覧との差分蓄積を防ぐため、同一PR内で反映します。

**チェック項目:**

- [ ] スキルを新規追加した場合、READMEの「スキル」一覧に追記したか？（Workflow / Atomic の区分も適切か？）
- [ ] スキルを削除した場合、READMEの「スキル」一覧から該当行を削除したか？
- [ ] スキルの `description` を変更した場合、READMEの「説明」列も同じ表現に揃えたか？
- [ ] 実行例（`/base-tools:<skill-name>` 等）がある場合、引数仕様と整合しているか？
